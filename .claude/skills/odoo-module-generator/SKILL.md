# Odoo module generator (OCA)

Produce addons that a consultancy can maintain and migrate: minimal custom code,
correct inheritance, security by default, tests always.

## Step 0 — Decide before writing code

Answer these in order and tell the user the answer in 2-3 lines:

1. **Standard / parametrization?** Configuration, automated actions, properties fields,
   record rules, server actions, Studio (Enterprise). If yes, propose it and stop.
2. **Existing OCA module?** Search `https://github.com/OCA` for the target branch
   (e.g. `OCA/account-financial-tools`, `OCA/l10n-spain`). Reuse > rewrite.
3. **Custom module**, minimal and by inheritance. Never touch core or OCA code.

When there are alternatives, show a table with: *Impacto en tiempos de entrega ·
Mantenibilidad a largo plazo · Coste de desarrollo · Cuándo elegirla*.

## Step 1 — Gather the minimum spec

Ask only what is missing: technical name (snake_case, English, prefixed by the base
module it extends: `sale_order_xxx`, `l10n_es_xxx`), Odoo series, `depends`, new models
vs inherited ones, who uses it (groups), multi-company yes/no, licence
(LGPL-3 default here; AGPL-3 if it goes to OCA).

## Step 2 — Scaffold

```bash
# --model: repeat per new model · --depends: minimal list · --dest: addons dir
python .claude/skills/odoo-module-generator/scripts/scaffold.py <name> \
  --model <a.b> [--model <c.d>] --depends base --version 19.0 --dest <addons_dir>
# Extension module without new models:
python .claude/skills/odoo-module-generator/scripts/scaffold.py sale_order_xxx \
  --depends sale --inherit-only --dest <addons_dir>
```

It generates manifest, models (company-aware, `models.Constraint`), list/form/search
views, action, menus, groups with `res.groups.privilege` (19.0), ACLs, multi-company
record rules, an access test and `readme/` fragments. It is verified to install and
pass its tests on 19.0. Then delete what the module does not need.

For other series, check the differences table below and adapt before running.

## Step 3 — Implement

- Class order: private attrs → `_default_*` → fields → `_compute_*/_inverse_*/_search_*`
  → `_selection_*` → constraints/onchange → CRUD overrides → `action_*` → `_business()`.
- Naming: `partner_id`, `line_ids`, `_compute_<field>`, `_check_<rule>`, `action_<verb>`.
- Type hints on public/business methods; docstring when the logic is not obvious.
- `@api.model_create_multi` + `vals_list`; always call and return `super()`.
- Pure business arithmetic (taxes, pricing, scoring) goes in a plain Python module
  without Odoo imports so it can be unit tested (see `services/tax_engine.py`).
- Translations: `self.env._("Text %(x)s", x=value)`; no f-strings inside.
- No `search()` inside loops, no `cr.commit()`, no `sudo()` without
  `# sudo: <reason>`, no SQL string interpolation (use `odoo.tools.SQL`).
- Configurable values (rates, thresholds) → data records or `res.config.settings`,
  never constants in code.
- External libraries → `external_dependencies` + guarded import.
- XML IDs: `<model>_view_form|list|search`, `<model>_action`, `<model>_menu`,
  `group_<module>_<role>`, `<model>_rule_<scope>`. `noupdate="1"` for data the
  customer may edit.
- Views 17+: `invisible="expr"` (no `attrs`). 18+: `<list>`, `view_mode="list,form"`.

## Step 4 — Security checklist (mandatory)

- [ ] ACL line for every model, TransientModel included. `unlink` only for managers.
- [ ] Record rules for company/owner segregation; `_check_company_auto` +
      `check_company=True` on relevant Many2one.
- [ ] Permission checked in Python, not just by hiding buttons.
- [ ] Controllers: explicit `auth`, `methods`, `csrf`; whitelist of written fields;
      `request.not_found()` instead of returning error dicts.
- [ ] No secrets in repo; sensitive fields with `groups=`.

## Step 5 — Tests and verification

- Business logic, constraints and **access** (`new_test_user` + `with_user`).
- Run: `odoo-bin -c odoo.conf -d test_db -i <module> --test-enable --test-tags=/<module> --stop-after-init`
  (`-i` install · `--test-tags=/<module>` filter by module · `--stop-after-init` exit at the end).
- Lint: `pylint --load-plugins=pylint_odoo --disable=all --enable=odoolint --valid-odoo-versions=19.0 <module>`
  and `ruff check`. `C8101` (OCA author) and `C8112` (README.rst, generated by
  `oca-gen-addon-readme` from `readme/`) are expected outside the OCA.
- Never report "done" without having run the tests.

## Step 6 — Deliver

1. Short analysis (standard/OCA/custom). 2. File tree. 3. Code per file.
4. Security added and why. 5. Tests. 6. How to test (commands with flags explained).
7. Migration risks / technical debt. Commit as `[ADD] <module>: ...` or `[IMP] ...`.

## Review mode (existing module)

Run both linters, then check: repo layout (one addon per folder, pre-commit from
`oca-addons-repo-template`), manifest keys (`website`, `external_dependencies`,
version `<series>.x.y.z`), folder names (`wizards/`, `readme/`, `i18n/`), XML ID
naming, ACL coverage, record rules, tests present, controllers, crons using
savepoints. Report findings ordered by severity with `file:line`.

## Version differences to verify

| Change | Since |
|---|---|
| `attrs`/`states` removed; `_compute_display_name` instead of `name_get` | 17.0 |
| `group_operator` → `aggregator`; `odoo.tools.SQL` | 17.0 |
| `<tree>` → `<list>`; `check_access(op)`; `self.env._()` | 18.0 |
| `_sql_constraints` → `models.Constraint`; `res.groups.privilege` replaces category on groups; `type="jsonrpc"` routes | 19.0 |

If unsure an API exists in the target series, grep the Odoo source of that branch
before using it and say so explicitly.
